# ecommerce-agent 架构演进路线图（v0.2 → v1.0）

> 建档 2026-08-14。**本文件是总纲**，每个版本的目的/方案/实测结果留档在 `docs/iterations/vX.Y-*/`。
> 起点：`5bb331b` initial commit + `2b5e61a` README —— CLI 交互式玩具，1400 行 src，79 用例。
> 终点：支持多轮记忆 / 多 Agent 路由 / 多轮意图识别 / 计费检测 / 文本安全检测 / 流式输出，
> 覆盖电商全流程场景，**以标准 HTTP + SSE 服务对外提供能力**（而非终端输入）。

## 二、技术选型（已定，不再反复）

| 维度 | 选型 | 决策依据 |
|---|---|---|
| 对外协议 | **HTTP + SSE**（`POST /v1/chat`） | 与现有 `AgentEvent` 六种事件天然对齐；接入成本最低；无状态易水平扩容 |
| HTTP 框架 | **Fastify** | SSE 支持好、性能优于 Express、TS 类型完备、`inject()` 让 SSE 测试不用起真端口 |
| 主存储 | **PostgreSQL** | 会话/消息/记忆/计费账本/审计都需要关系查询与事务；计费一致性不能靠文件 |
| 缓存/计数 | **Redis** | 会话热缓存、配额计数器、限流令牌桶——这三件事都要原子操作 |
| 存储访问 | **Store 接口 + 多实现** | 接口先定，PG 为默认实现，内存实现供单测。换存储只换实现类 |
| 多 Agent | **进程内 Router（v0.9）→ 微服务拆分（v0.15）** | 边界未稳定就物理拆分 = 返工成本 × 服务数。先在单进程验证边界，稳定后再拆 |
| 模型 | `claude-opus-5` 默认，`claude-sonnet-5` 可配 | 当前默认 `claude-sonnet-4-20250514` 已 deprecated（2026-06-15 退役） |
| 测试 | vitest（单元/集成）+ docker-compose（PG/Redis 集成） | 沿用现有栈，不引入第二套 runner |

## 四、每版交付物与留档规范（强制）

每个版本目录 `docs/iterations/vX.Y-<slug>/` 下三份文档，缺一不算完成：

| 文档 | 内容 | 写作时机 |
|---|---|---|
| `SPEC.md` | **迭代目的**（为什么现在做这个）、**边界**（做什么 / 明确不做什么）、验收标准（可执行的判据） | 开工前 |
| `PLAN.md` | 文件清单（新建/修改，精确到路径与行号）、接口签名（消费什么/产出什么）、TDD 逐步骤（红→绿→提交）、风险预判 | 开工前 |
| `REPORT.md` | **实测结果**：测试命令与完整输出、before/after 对比证据、偏离计划之处及原因、遗留问题 | 完工后 |

**Tag 规范**：每版完成后打 annotated tag，message 首行为版本主题，正文指向该版本文档目录。

```bash
git tag -a v0.2 -m "v0.2 接线与地基：Guardrail 管道化 + 工具统一

文档: docs/iterations/v0.2-wire-up/
核心设计: Guardrail 中间件管道化、工具统一走 ToolRegistry
修掉缺陷: 5 个（详见 REPORT.md）"
git push origin v0.2
```

**验收铁律**（来自 superpowers `verification-before-completion`）：
没有在当轮跑过验证命令，就不准声称"通过"。`REPORT.md` 里的每条结论必须附命令与输出，
"应该没问题""看起来对了"一律不算。回归测试必须走红-绿验证：写测试→跑通过→撤掉修复→**必须失败**→恢复→再跑通过。

### 偏离 SPEC 的处理规矩（2026-08-15 立，来自苏姐巡检）

v0.2 和 v0.3 都出现了「中途越界 → 只在 REPORT 第五节解释」。一次是失误，两次是流程默认值，
后果是 **SPEC 永久与实际交付不符** —— 半年后拿 SPEC 逐条核验的人，必须交叉引用 REPORT
才能判断某件事是否被授权。文档的价值在于不用交叉引用就能取信。

**规矩：偏离 SPEC → 先回去改 SPEC（在 ✅ 清单加一行，注明「中途追加 · 原因：X」）→ 再动手。**
`REPORT.md` 第五节只记录「改了 SPEC 之后仍然出现的偏离」。SPEC 始终是本版实际契约的单一事实来源。

### 当版补洞的准入线（同上）

不是所有发现的问题都该当版修。判据两条，**必须同时满足**：

1. 这个缺口是**本版改动亲自触发的**
2. **不补就会在本版内继续误导验收**

其余一律进遗留问题表**并指定归属版本**（不允许只写「以后再说」）。

- ✅ 通过的例子：v0.3 补 `tsconfig.test.json` —— 改名 `toolUse→toolUses` 亲自触发，
  且已真实造成一次误诊（类型漏改伪装成「不变量断言失败」，误导排查方向）
- ❌ 不通过的例子：eslint / CI / 覆盖率门 —— 都不是本版触发的，也不会误导本版验收，
  整体归 **v0.14 可观测与评测**

判断蔓延与否的尺子：**这件事有没有改变本版的交付面或风险面？** 只是让既有交付面变得可验证 → 不算蔓延；
多出一个能力或多出一条未被 SPEC 边界约束的失败路径 → 是蔓延。

## 五、版本间依赖（不可乱序的部分）

```
v0.2 ──▶ v0.3 ──▶ v0.4 ──┐
 接线     正确性    流式     │
                          ├──▶ v0.6 ──▶ v0.7 ──▶ v0.8 ──▶ v0.9 ──┐
          v0.5 ───────────┘   服务化    记忆     意图     路由      │
          存储层                                                    │
                                                                    ├──▶ v0.12 ─▶ v0.13 ─▶ v0.14 ─▶ v0.15 ─▶ v1.0
                          v0.10 ──▶ v0.11 ─────────────────────────┘    场景I    场景II   可观测   拆服务   生产化
                           安全       计费
```

- **v0.5 存储层必须先于 v0.6 服务化**：服务化后会话不能再存进程内存
- **v0.7 记忆必须先于 v0.8 意图**：多轮意图继承依赖记忆里的上下文
- **v0.8 意图必须先于 v0.9 路由**：路由的输入就是意图识别的输出
- **v0.11 计费必须先于 v0.15 拆分**：计费口径要在单进程里对齐，拆开后再对齐成本翻倍
- **v0.14 评测必须先于 v0.15 拆分**：没有回归基线就拆服务 = 没有安全网走钢丝
