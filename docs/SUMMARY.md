## 二、17 个版本，每版解决了什么

| 版本 | 主题 | 核心设计 | 修掉的"看起来在工作但实际没有" |
|---|---|---|---|
| v0.2 | 接线与地基 | Guardrail 管道化、工具统一注册 | **4 组模块运行时零引用** —— 代码写了、测试绿了，管道里根本没接 |
| v0.3 | 核心链路正确性 | 并行工具调用、事件溯源可 restore | 模型返回多个 `tool_use` 时只取第一个；退款不幂等 |
| v0.4 | 流式输出 | `messages.stream()` + **EventBus** | 首字要等 613ms。验收判据从此必须是用户可感知的 |
| v0.5 | 存储层 | Store 接口族 + PG/PGlite + 迁移 | JSONL 无并发保护；按 `created_at` 排序而 PG 的 `now()` 是事务开始时间 |
| v0.6 | **服务化** | Fastify + SSE，CLI 降级为瘦客户端 | flaky 测试暴露的**真** bug —— flaky 是并发缺陷的唯一自动信号 |
| v0.7 | 多轮记忆 | 三层记忆 + Redis 热缓存 | 缓存 token 漏算：`input_tokens` 只是未命中缓存的部分 |
| v0.8 | 多轮意图识别 | 意图 + 槽位 + 置信度 + 状态机 | 模糊问题不澄清、话题切换串线 |
| v0.9 | 多 Agent 路由 | AgentRegistry + IntentRouter | 收窄工具面本身就是准确率手段 |
| v0.10 | 文本安全 | 四级处置 + 审计 + **流式脱敏** | 脱敏保护的是**返回值**，而用户看的是流 —— 未脱敏手机号早已打到屏幕上 |
| v0.11 | 计费与配额 | 持久化账本 + 两级配额 | `maxTokensPerSession` **限的不是 session** —— 同会话 300k 一次不拦 |
| v0.12 | 电商场景 I | 业务流状态机 + 异步确认 | 退款在服务端根本执行不了，且失败信息**谎称"用户取消"**，模型据此回"已处理" |
| v0.13 | 电商场景 II | Artifact 结构化返回 + 多租户配置 | 对外只有文本 API，接入方只能正则解析中文散文 |
| v0.14 | 可观测与评测 | 指标 + 离线评测 + 三维回归门 | `ResponseScorer` 越啰嗦分越高，且**十三个版本没人读过它** |
| v0.15 | 微服务拆分 | `ToolGateway` 接口取代具体类 | `tool.execute` 是函数引用 —— **跨不了进程，是架构死结不是性能问题** |
| v1.0 | 生产化收口 | 熔断重试 + 取消传播 + 优雅退出 | 客户端断开后 Loop 继续跑完 —— 给没人看的回答付真钱 |
| v1.1 | 身份与租户边界 | Principal + 越权 404 + 限流 + 幂等 | **`tenant_id` 由客户端声明**；画像按 `user_id` 单列存 → 跨租户 PII 泄露 |
| v1.2 | 错误·并发·追踪·清理 | `TurnResult` + 会话锁 + span + sweeper | 失败正文**冒充回复**；并发把会话历史写交错，延迟一轮才发作 |

## 三、这个项目真正的产出：那张缺陷账本

17 版挖出 20 个「看起来在工作但实际没有」。**共同点全部是：单元测试全绿，端到端行为是错的。**

按"发现它需要什么"分三类：

### ① 沿用户真实路径从头跑一遍才会发现

| 版本 | 缺陷 | 表现 vs 真相 |
|---|---|---|
| v0.2 | 能力没接进管道 | 表现：功能"做完了"｜真相：运行时零引用 |
| v0.10 | 流式绕过输出脱敏 | 表现：脱敏用例全绿｜真相：用户屏幕上是未脱敏的手机号 |
| v0.11 | 配额限的不是 session | 表现：有熔断代码｜真相：计数器每请求新建，永不触发 |
| v0.12 | 高危工具在服务端一律拒绝 | 表现：客户收到"已处理"｜真相：退款从没执行过 |
| v0.13 | 结构化数据出门前被丢掉 | 表现：接口有返回｜真相：接入方只能正则解析中文 |
| v1.1 | `tenant_id` 客户端自称 | 表现：多租户做了五个版本｜真相：改一个 JSON 字段就能烧别人的额度 |
| v1.2 | 错误正文冒充回复 | 表现：HTTP 200｜真相：CLI 把 `LLM调用失败: xxx` 逐字打给用户 |

### ② 数据模型缺一维，只能靠迁移修

| 版本 | 缺陷 |
|---|---|
| v0.5→v0.6 | 用 `created_at` 排序 —— PG 的 `now()` 是**事务开始时间**，同毫秒记录顺序随机 |
| v1.1 | `user_profiles` 主键是 `user_id` 单列 —— 而 user_id 常是**手机号，可枚举**，任何租户拿它就能读到别家客户的称呼、收货偏好、投诉备注 |
| v1.2 | 会话无并发控制 —— 追加式存储不会覆盖，但会**交错**，`tool_use` 与 `tool_result` 被隔开，下一轮 restore 出来就是坏的 |

### ③ 建好了却没人用（最隐蔽的一类）

| 版本 | 缺陷 | 活了多久 |
|---|---|---|
| v0.14 | `ResponseScorer` 每轮写一个假分数，越啰嗦分越高 | **13 个版本没有任何代码读它** |
| v1.1 | `UserProfileManager` —— v0.1 遗留的第二套画像实现 | **16 个版本零生产引用** |
| v1.2 | 幂等记录的 `expires_at` 建好了，没有任何东西读它 | 1 个版本，表只增不减 |
| v0.14 | 被拦下的工具调用不发任何事件 | 指标偏低，且偏低的正是最该关注的那部分 |

### ④ 架构死结（不是性能问题）

- **v0.15** `tool.execute` 是函数引用 —— 跨不了进程。这不是"慢"，是拆不开。
- **v1.1** 拆分形态下 `tool-service` 完全没有认证 —— 绕过主服务直接打它，v0.12 的高危确认流根本不存在。
- **v1.2** `/v1/traces` 归属判定第一版按「逐 span 过滤 tenant」，而 model/tool span 根本没有 tenant 属性 → 直接漏给任何人。**默认放行 + 逐项排除，在数据缺失时会静默放行。**

## 四、反复被验证的六条方法论

### 1. 动手前先把失效的样子固定成用例

从 v0.11 起成为固定动作。修完才**证得了**修好了 —— 否则"我觉得修好了"和"真的修好了"没有区别。

v1.1 的画像泄露就是这么锁住的：先在 v1.0 的代码上跑探针，让它打印出租户 B 读到的租户 A 客户信息，再动手。

### 2. 红-绿验证（断电）：撤掉修复，必须变红

不是形式主义。它两次抓到"通过但测的是别的东西"：

- **v1.1**：拿掉确认单的防重放守卫，**一条用例都不红** —— 我那组"防重放"测试测的根本是别的东西。补了 4 条直接的库级用例后重新验证。
- **v1.2**：`purgeExpired` 不看过期时间就全删，**6 条红**；拿不到会话锁也放行，**4 条红**。

七个版本累计做了 17 组断电验证，全部转红后恢复。

### 3. 默认值要站在出错时损失最小的那一侧

| 地方 | 默认值 | 为什么 |
|---|---|---|
| `withRetry.isRetryable` | 都**不**重试 | 重试一个可能已经生效的写操作 = 重复退款 |
| 高风险工具 | **永不**重试 | 超时最可能是响应丢了而请求已在下游执行完 |
| 认证 | **默认开启** | 关掉要显式设环境变量，且启动时打警告 |
| 租户安全规则 | 只能**加严**不能放宽 | 同 id 的规则被忽略而不是覆盖 |
| 限流的 Redis 降级 | 降级到进程内**限流**，不是放行 | 与缓存相反：故障期恰恰最需要限流 |

### 4. 失败必须看起来像失败

这是全项目重复次数最多的一条，从 v0.12 到 v1.2 一直在修同一个物种：

- v0.12 退款失败却说"用户取消了该操作"→ 模型据此回客户"已处理"
- v1.1 模型挂了却回 200，错误正文当回复正文
- v1.2 `TurnResult` 里失败时 `reply` 是空串 ——「失败时给一句像样的话」听起来贴心，实际是让失败伪装成回答

### 5. 抽象好不好，看后来加东西时改了几个文件

`EventBus`（v0.4）是全程最划算的一笔投资：SSE 写出（v0.6）、安全事件（v0.10）、指标采集（v0.14）、span（v1.2）四次接入都只是"加一个订阅者"，`AgentLoop` 一行没改。

反例同样清楚：`ToolRegistry` 是具体类，于是 v0.15 拆服务时必须先改成接口。

### 6. 诚实标注没验证过的东西

- Docker 与 compose **未经构建验证**（开发机无 Docker）—— 标在 Dockerfile 首行、`deploy/README.md`、README 部署段三处
- 配额"先检查后扣减"有超发，上限 = 并发 × 单轮用量，**可实测**（`npm run bench:quota`）
- 限流在多实例下是 N 倍配额 —— 写进 `/healthz` 的 `rate_limit` 字段
- `/v1/traces` 只看得到本实例的缓冲 —— 写进响应体的 `note`

> 交付一个自己没验证过的东西，唯一能做的补救是**说清楚它没被验证**。假装它跑过，比不提供它更糟。

## 五、现在还差什么

### 已明确不做（附理由）

| 事项 | 为什么 |
|---|---|
| 配额精确扣减 | 需要预留-提交，代价是处理预留泄漏；超发上限有界可测，不值得 |
| span 采样 | **没有真实流量数据就定采样率是拍脑袋** |
| 密钥自动轮转 | issue + revoke 够了，轮转是运维流程不是代码决定 |
| SSE 响应重放 | 流里有 `confirmation_required` 这类当时才成立的事件，重放会让客户端弹出早已决策过的确认框 |
| 跨实例链路查询 | 要全局就该上真 collector —— OTLP 已经通了 |

### v1.3 的三条（它们是一组）

| # | 事项 |
|---|---|
| D-8 | 模型 provider fallback |
| D-9 | Prompt 版本管理与灰度 |
| D-10 | 答案质量评测（LLM-as-judge + 人工标注集） |

**必须一起做**：没有 D-10，就无法判断 fallback 模型或新版 prompt 是不是让效果变差了 ——
先做前两条等于给自己装一个看不见后果的开关。这正是这个项目一路在修的那个物种，
只不过这次是在事前认出来的。

### P2 合规与运维（未动）

数据保留期与删除接口、日志脱敏、告警规则与 SLO 定义、转人工工单闭环、
K8s/灰度/多区域、真实压测与容量模型、密钥 vault。

## 六、一句话

**这个项目值得读的不是它做了什么，是它在每一版里发现了什么。**

功能清单是可复制的；「单元测试全绿而端到端行为是错的」这类问题的**发现方式**不是。
抓住它们的唯一办法，是沿用户真实走的那条路从头跑一遍，
并且**先把失效的样子固定成用例再动手修**。
