# v0.11 · 计费与配额（Billing & Quota）

> 起点 `a6ebc43`（v0.10）｜ 后继 v0.12 电商场景 I
> **还 v0.2 欠的账**：`maxTokensPerSession` 这个名字是假的。

---

## 一、迭代目的

### 🔴 先说清楚现在有多糟

v0.2 接线时给管道挂了 `BudgetGuard`，测试全绿，看起来预算熔断已经生效。
实测（探针脚本，5 轮同会话请求）：

```
第0轮: blocked=undefined     第3轮: blocked=undefined
第1轮: blocked=undefined     第4轮: blocked=undefined
第2轮: blocked=undefined     模型总共被调用 5 次
```

**同一个会话烧掉 300,500 tokens，上限写着 100,000，一次都没拦。**

原因在 `prepareTurn` 里一行：

```ts
const tracker = new TokenTracker();   // ← 每个 HTTP 请求新建
```

于是 `maxTokensPerSession` 实际限制的是**单个 HTTP 请求内多轮工具调用之间**的用量。
纯文本回复的场景下一个请求只调一次模型，计数器从 0 开始、加一次、随请求销毁——
**熔断永远不可能触发。**

这是 v0.2「测试全绿 ≠ 能力生效」的第三次发作，前两次是：
- v0.2：能力写好了但没接进管道（接线解决）
- v0.10：脱敏接了但保护的是返回值而非用户看的流（双出口只测一条）
- **v0.11（本次）：接了、通了、口径也对，但状态活不过一个请求**

### 三个必须一起解决的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 用量状态在进程内存里，随请求销毁 | 配额形同虚设；进程重启账目清零 |
| 2 | 没有租户维度 | 多租户下无法计费、无法按租户限流 |
| 3 | 并发下的检查-扣减非原子 | 两个请求同时读到「还剩 1%」，双双放行 |

## 二、核心设计

### ⚙️ 设计① 持久化计费账本（真相在库里，不在内存里）

每次模型调用落一条 `usage_records`：租户、会话、模型、四类 token、成本、时刻。

```
usage_records
  ├── tenant_id    ← 计费与配额的主维度
  ├── session_id   ← 会话级配额
  ├── model        ← 不同模型不同价
  ├── input/output/cache_read/cache_write_tokens
  ├── cost_usd     ← 按**调用当时**的价格算好落库（v0.3 的 PriceWindow）
  └── seq          ← BIGSERIAL，排序靠它不靠时间戳（v0.5 的教训）
```

**成本在写入时定格，不在查询时重算。** 价格会变，历史账单不该跟着变——
这是财务数据的基本要求，也是 v0.3 做时间窗定价时就该想到的。

### ⚙️ 设计② 两级配额：租户 + 会话

| 级别 | 限什么 | 越限后 |
|---|---|---|
| 会话 | 单会话累计 token | 提示开新会话（可恢复） |
| 租户 | 租户在计费周期内累计 token | HTTP 429（需要充值/提额） |

会话级越限**不是错误**，是正常的对话长度管理，仍返回 200 + `blocked` 明细。
租户级越限是**商业事件**，必须是 429 —— 调用方要能靠状态码区分「换个会话继续」
和「你欠费了」。

### ⚙️ 设计③ 热路径读缓存，扣减用原子操作

每请求查一次库做配额检查，是把库放在了每一个请求的关键路径上。

```
检查：Redis 计数器（毫秒级）── 未命中 ──▶ 回库聚合 ──▶ 回填
扣减：Redis INCRBY（原子，返回新值）+ 异步落库账本
兜底：Redis 不可用 → 全部回库，慢但正确（延续 v0.7 的降级原则）
```

**关于并发的诚实说明**：本版采用「先检查、后扣减」，这意味着 N 个并发请求可能
同时通过检查后各自扣减，出现**超发**。超发上限 = 并发数 × 单轮最大用量。
不假装它是精确的——而是**测出这个上限并写进文档**。要做到精确扣减需要预留额度
（reserve-then-commit），那会引入「预留泄漏」问题，不值得在这一版做。

## 三、边界

### ✅ 本版做

| # | 事项 | 类型 |
|---|---|---|
| 1 | 迁移 `004_usage_records` | 设计① |
| 2 | `PgUsageStore`：追加记录 + 按租户/会话聚合 | 设计① |
| 3 | `AgentLoop` 增 `onUsage` 钩子，每次模型调用落账 | 设计① |
| 4 | `QuotaService`：两级配额检查，Redis 加速 + 库兜底 | 设计②③ |
| 5 | `quota.mw.ts` 取代 `budget-guard.mw.ts` | 设计② |
| 6 | **修好跨请求的会话配额**（本版的核心 bug） | 设计① |
| 7 | 租户越限返回 **429** + `quota_exceeded` | 设计② |
| 8 | `GET /v1/tenants/:tenant_id/usage` 查账 | 🛒 |
| 9 | 并发超发上限的实测与文档化 | 设计③ |

### ❌ 本版不做

| 事项 | 留给 | 理由 |
|---|---|---|
| 计费周期结算/账单生成 | 不做 | 账本是原料，出账是另一个系统的事 |
| 按租户配不同价格 | 不做 | 需要合同模型，超出 agent 范畴 |
| 预留-提交式精确扣减 | 不做 | 引入预留泄漏问题，收益不抵复杂度（见设计③） |
| 按租户配不同安全规则集（v0.10 承诺） | v0.13 | 租户模型本版才建立，规则集下沉排在场景版之后 |

## 五、风险预判

| 风险 | 影响 | 缓解 |
|---|---|---|
| 每请求多打一次库做配额检查 | 延迟上升 | Redis 计数器挡住热路径；实测给出有/无缓存的延迟差 |
| 账本写入失败拖垮对话 | 单点故障 | 落账失败只记警告不阻断（延续 v0.7/v0.10 原则）；但**配额检查失败必须拦**——放行等于免费送 |
| 并发超发 | 商业损失 | 测出上限并文档化；上限 = 并发 × 单轮用量，对 token 计费来说可接受 |
| 修好配额后既有用例被拦 | 大面积转红 | 测试配置调高上限；**拦截是正确行为，不能靠调低期望绕过** |
| 租户 id 缺失（匿名调用） | 配额无处可挂 | 无 tenant_id 时只做会话级配额，账本记 `anonymous` |
