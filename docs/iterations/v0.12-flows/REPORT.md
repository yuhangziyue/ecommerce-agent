# v0.12 迭代报告 · 电商场景 I（业务流与异步确认）

> 起点 `8e49afa`（v0.11）｜ 用例 **433 → 496**（+63）｜ `npm run verify` exit 0
> **本版还清了 v0.6 欠的账：服务端的退款一直是死的，而且失败信息在撒谎。**

---

## 一、修之前：这个电商 Agent 不能退款

前十一版把地基打得很扎实 —— 流式、存储、记忆、意图、路由、安全、计费。
探针一跑，最核心的业务动作是死的：

```
用户: 我要退款
模型: [调用 refund_apply]
工具: 用户取消了该操作。          ← ①
模型: 已处理                      ← ②
```

**① 这句话是假的。** 用户从没取消过任何东西。真实原因是 v0.6 给服务端写死了
`onConfirm: async () => false`。当时的判断没错（HTTP 确实没有同步确认通道），
错在**把技术原因伪装成了用户行为** —— 排查的人会去查用户干了什么，而那里什么都没有。

**② 假信息造成了连锁错误。** 模型拿到「用户取消了」，合理地推断出事情办完了，
回了句「已处理」。客户以为退款提交了，实际什么都没发生，日志里没有任何异常。

> 一个错误的错误信息，比没有错误信息更糟：
> 它不只是没提供线索，还**主动把人引向错误的方向**，
> 而且让下游（这里是模型）基于假前提做出更错的决定。

## 三、核心设计的实际结果

### ⚙️ 设计① 异步确认 —— 关键是那句话必须是真的

```ts
it('🔴 第一轮不执行，但工具结果说的是真话（不再谎称「用户取消」）', async () => {
  const result = provider.lastToolResults[0];
  expect(result).not.toContain('取消');
  expect(result).toContain('需要客户确认');
  expect(result).toContain('cfm_');
});
```

「等待客户确认」让模型做出正确的下一步（请客户去确认）；
「用户取消了」让模型做出错误的下一步（宣布已处理）。
**同一个「不执行」的结果，两句不同的话，下游行为完全相反。**

端到端现在真的能走完：

```ts
await chat('我要退款');                                  // 生成确认单
await POST(`/v1/confirmations/${id}`, { approved: true }); // 客户确认
await chat('已确认，请处理', sessionId);                   // 真正执行

expect(executed).toContain('退款工单号');
const { rows } = await db.query('SELECT * FROM refund_tickets');
expect(rows).toHaveLength(1);   // 不是只在文案里说了一句
```

`ConfirmHandler` 的改法是**只扩不改**：仍接受 `boolean`（CLI 一行没动），
新增的对象形态只是让拒绝理由能说真话。改签名比改语义安全得多。

### ⚙️ 设计② 状态机 —— 拒绝理由要带具体数字

守卫的返回值刻意不是 `boolean` 而是 `{ok:false, reason}`，因为
**这个理由会原样传给模型、再由模型转述给客户**：

```ts
it('🔴 超出售后时效被拒，理由带具体天数（客户才知道差多少）', async () => {
  expect(reason).toContain('12 天');   // 实际签收天数
  expect(reason).toContain('7 天');    // 政策时效
  expect(reason).toContain('人工');    // 还有什么出路
});
```

「不符合退货条件」是不合格的话术。「已签收 12 天，超出 7 天时效，
如有质量问题可转人工」才是客户能据以行动的信息。

非法流转的报错也带上「当前能做什么」，让模型能自我纠正而不是反复试错：

```
当前状态「reviewing」不支持「complete」。当前可执行：approve、reject、cancel。
```

状态落库带来的直接收益：**上下文裁剪与服务重启都不影响流程**。
v0.7 的滑窗/摘要压缩会裁掉历史，而流程状态根本不在上下文里。

### ⚙️ 设计③ 审批分档

金额 ≤ 门槛自动批准，超过则必须带审批人。门槛是**业务参数**（`ReturnPolicy`），
运营调它不该改代码 —— 用例里直接把门槛调成 1 和 100000 验证两侧行为。

## 四、过程中发现的问题

### 🔴 我自己差点写出一个并发串号 bug

`return_request` 需要知道当前会话号。第一版照搬了 `setRefundStore` 的模块级注入：

```ts
let currentSessionId = '';                              // ← 灾难
export function setFlowEngine(e, sessionId) { … }
```

`setRefundStore` 那样写没问题（进程级依赖，无请求态），但 **sessionId 是请求态**。
服务端并发处理多个请求时，后来的请求会覆盖「当前会话」——
**甲客户的退货会记到乙客户名下**，且只在有并发时出现，本地单请求测试永远发现不了。

改为在 `AgentTool.execute(params, ctx)` 里传：一处调用点、向后兼容、
且**类型层面消除了这个可能性**，不靠自觉。

> 模式相似不等于约束相同。抄一个既有写法之前，
> 要先问它成立的前提是什么 —— 这里的前提是「被注入的东西没有请求态」。

### 🔴 红绿验证暴露出我的「防重放」测试测的是别的东西

拿掉 `consume()` 的 `WHERE status = 'approved'` 守卫后，**一个用例都没红**。

查下来：那几条「确认单不可重放」的用例，实际拦截发生在 `findDecided()` 的状态过滤
（已消费的单 status 是 `consumed`，不在 `approved/rejected` 里，所以找不到）。
而 `consume` 的 WHERE 子句防的是**并发**重放 —— 两个请求同时拿到同一张已批准的单，
那条路径当时零覆盖。

补了 4 条直接打 store 的用例后再断电，4 条全红。

> 红绿验证的价值不只是「确认测试有效」，更是**确认测试在测你以为的那个东西**。
> 一条绿色的用例可能因为完全不同的原因而绿 —— 断电才问得出来。

### 🟡 测试假 provider 的一个判据错误

`RefundProvider` 用 `messages.find(m => m.role === 'tool')` 判断「工具已执行完」，
但第二轮的会话历史里**本来就有上一轮的 tool 消息** —— 于是模型永远不再调用工具，
三条端到端用例莫名失败。改成看**最后一条**消息。

这是测试替身的 bug 不是产品的 bug，但值得记：
**多轮场景下，「历史里有没有」和「刚刚发生了没有」是两件事。**
