# v0.12 · 电商场景 I（业务流与异步确认）

> 起点 `8e49afa`（v0.11）｜ 后继 v0.13 电商场景 II
> **还 v0.6 欠的账**：服务端一律拒绝高风险工具 —— 退款在线上根本执行不了。

---

## 一、迭代目的

### 🔴 先说清楚现在有多糟

前十一版把地基打得很扎实：流式、存储、记忆、意图、路由、安全、计费。
但探针一跑，**这个电商 Agent 最核心的业务动作在服务端是死的**：

```
用户: 我要退款
模型: [调用 refund_apply]
工具: 用户取消了该操作。          ← ①
模型: 已处理                      ← ②
```

两处都错，而且是叠加的错：

① **这句话是假的。** 用户从没取消过任何东西。真实原因是 v0.6 给服务端写死了
`onConfirm: async () => false` —— 服务端没有交互式确认通道，于是高风险工具一律拒绝。
但拒绝的理由被伪装成了「用户取消」，**排查的人会去查用户干了什么，而那里什么都没有**。

② 模型拿到「用户取消了」这个假信息，合理地推断出事情办完了，回了句「已处理」。
**客户以为退款申请提交了，实际上什么都没发生。**

这不是小 bug，这是**一个电商客服 Agent 唯一不能出错的地方出了错**。

### 三个必须一起解决的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 高风险操作在服务端无法执行，且失败信息撒谎 | 核心业务动作不可用，且不可排查 |
| 2 | 退款是「一次调用直接建单」，没有审批 | 金额多大都直接放行，没有任何业务风控 |
| 3 | 多步业务流（退货/换货）没有状态，全靠模型记 | 上下文一裁剪流程就断，且不可恢复、不可审计 |

## 二、核心设计

### ⚙️ 设计① 异步确认（还 v0.6 的账）

问题的本质：**CLI 的确认是同步的（等用户敲 y），HTTP 的确认不可能同步** ——
请求不能挂在那里等人点确认。v0.6 的处置是「一律拒绝」，等于把能力砍掉。

正确的解法是把确认变成**一次独立的往返**：

```
第 1 轮  用户: 我要退款
        ├─ 模型调 refund_apply（高风险）
        ├─ 不执行，落一条 pending 确认单
        ├─ 工具返回：「已生成确认单 cfm_xxx，等待客户确认」  ← 说真话
        └─ SSE 发 confirmation_required 事件
                    ↓
        客户端: POST /v1/confirmations/cfm_xxx {approved: true}
                    ↓
第 2 轮  用户: 确认
        └─ 工具检查到确认单已批准 → 真正执行
```

**关键是工具返回的话必须是真的。** 「等待客户确认」这句话让模型做出正确的下一步
（告诉客户去确认），而「用户取消了」让模型做出错误的下一步（宣布已处理）。

### ⚙️ 设计② 业务流状态机（持久化、可恢复、带守卫）

退货/换货不是一次调用能完成的：要核验订单状态、判断是否在时效内、确认退货原因、
生成退货地址、等待寄回、确认收货、发起退款。**这是一个有状态的多步流程。**

现在这个状态只存在于模型的上下文里 —— 上下文一裁剪（v0.7 的滑窗/压缩），流程就断了，
而且断得悄无声息。

```
                ┌──────────┐
                │ initiated│
                └────┬─────┘
        守卫: 订单已签收 且 在 7 天内
                     ▼
                ┌──────────┐      拒绝      ┌──────────┐
                │ reviewing├──────────────▶│ rejected │
                └────┬─────┘                └──────────┘
              批准   │
                     ▼
                ┌──────────┐               ┌──────────┐
                │ approved ├──────────────▶│ completed│
                └──────────┘   退款到账     └──────────┘
```

状态落库（`business_flows` 表），**每次流转都留痕**。这样：
- 上下文裁剪不影响流程（状态不在上下文里）
- 服务重启不影响流程
- 出了纠纷可以回放每一步是谁、什么时候、基于什么条件流转的

### ⚙️ 设计③ 审批规则：金额分档

| 条件 | 处置 |
|---|---|
| 金额 ≤ 200 且订单状态正常 | 自动批准 |
| 金额 > 200 | 转人工审批（落工单，不阻塞对话） |
| 超出售后时效 | 拒绝并说明具体天数 |
| 订单状态不允许（未付款/已退款） | 拒绝并给替代方案 |

**门槛值可配**，因为它是业务参数不是技术参数 —— 运营调它不该改代码。

| 10 | 工具：`logistics_check`（物流异常识别 + 处置建议） | 🛒 |
| 11 | **【追加 2026-08-15】** `ToolContext`：工具执行时拿到 sessionId，替代模块级变量 | 并发正确性 |

> **追加说明（11）**：`return_request` 需要知道当前会话号。最初照搬 `setRefundStore`
> 的模块级注入写法，把 sessionId 也存成模块变量 —— 那是**并发下的串号 bug**：
> 服务端同时处理多个请求时，后来的请求会覆盖「当前会话」，
> 表现为甲客户的退货记到乙客户名下，且本地单请求测试永远发现不了。
> 改为 `AgentTool.execute(params, ctx)` 传入，一处调用点，向后兼容。

## 五、风险预判

| 风险 | 影响 | 缓解 |
|---|---|---|
| 状态机过度设计 | 复杂度爆炸 | 只做一条流（退货退款），定义即数据；不做通用工作流引擎 |
| 异步确认改动 AgentLoop 核心 | 回归风险 | `onConfirm` 签名不变，返回值从 boolean 扩成带原因的对象；CLI 路径不受影响 |
| 确认单被重放 | 越权执行 | 确认单一次性消费，用后置终态 |
| 流程状态与工单状态不一致 | 数据打架 | 工单是流程的**产物**，不是并行的第二份状态 |
| 新表让 truncateAll 再咬一口 | 用例串数据 | v0.11 已改为从 `pg_tables` 查，自动覆盖新表 |
