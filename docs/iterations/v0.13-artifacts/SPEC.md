## 一、迭代目的

### 🔴 对外提供的是「文本 API」，不是「服务 API」

用户对这个项目的要求是**「能够对外提供标准的服务，而不是终端输入内容」**。
v0.6 做了 HTTP + SSE，看起来达成了。但把接口摊开看：

```
SSE tool_end  → { tool, duration_ms, is_error }
POST /v1/chat/sync → { session_id, reply, usage }
```

**全是文本和元信息，没有一个字段是业务数据。**

而工具明明算出来了。`product_search` 返回的 `metadata` 里有 productId、价格、库存、
评分；`refund_apply` 有工单号和金额；`return_request` 有流程号和状态。
这些数据被完整地写进了 session，**然后在到达调用方之前被丢掉**。

后果是：接入方想在 App 里渲染一张商品卡，只能去**解析模型生成的中文散文**——
从「无线蓝牙耳机Pro，售价 299 元，库存充足」里正则抠出价格。
模型换个说法（「售价￥299」「299元」「两百九十九」），解析就崩了。

> 一个「标准的服务」，判据不是「有没有 HTTP 接口」，
> 而是**调用方能不能不依赖自然语言解析就把功能用起来**。
> 按这个判据，前十二版交付的一直是个聊天接口。

## 二、核心设计

### ⚙️ 设计① 结构化返回协议（Artifact）

工具除了给模型看的 `content`（自然语言），再产出一份给调用方用的 `artifact`：

```ts
interface ToolArtifact {
  type: 'product_list' | 'order_card' | 'refund_ticket'
      | 'flow_status' | 'coupon_list' | 'invoice' | 'membership';
  data: unknown;   // 按 type 定形，各自有 TS 类型
}
```

**两份输出、两个受众，各司其职**：
- `content` 给模型 —— 自然语言，模型据此组织回复
- `artifact` 给调用方 —— 结构化，App 直接渲染卡片

关键约束：**artifact 不经过模型**。它从工具直接流到 SSE 与响应体，
中间不被复述、不被改写、不会因为模型换个说法就变形。

### ⚙️ 设计② 贯通到 API 表面

```
SSE:  tool_end → { tool, duration_ms, is_error, artifact }
                 新增 artifact 事件（单独一帧，便于客户端只订阅它）
Sync: { session_id, reply, artifacts: [...], usage }
```

`/v1/sessions/:id/artifacts` 可回放整个会话产出的全部结构化数据 ——
客户端断线重连后不必重跑对话就能恢复界面。

### ⚙️ 设计③ 租户配置（还 v0.10 / v0.12 的账）

```
TenantConfig {
  safetyRules?:  额外的输入/输出规则（叠加在全局之上，不是替换）
  returnPolicy?: 售后时效与自动批准门槛
  quotaLimits?:  配额上限
}
```

**叠加而非替换**是刻意的：安全规则如果允许租户「替换」，
一个配置失误就把全局的注入防护整个关掉了。租户只能**加严**，不能放宽。

## 五、风险预判

| 风险 | 影响 | 缓解 |
|---|---|---|
| artifact 与 content 不一致（说的和给的不是一回事） | 客户端与话术打架 | 两者**同源**：由同一份计算结果分别渲染，不各算各的 |
| 每个工具都要改，回归面大 | 破坏既有用例 | artifact 是**可选字段**，不产出也不影响既有行为 |
| 租户规则允许放宽 → 安全洞 | 一个配置失误关掉全局防护 | 类型上只提供「追加」接口，不提供替换；并写用例钉死 |
| 租户配置每请求查库 | 延迟上升 | 进程内缓存 + 显式失效；配置读多写极少 |
| artifact 体积过大撑爆 SSE 帧 | 流中断 | 列表类限条数（商品最多 20），并在 REPORT 记录上限 |
