# v0.14 迭代报告 · 可观测与评测

> 起点 `2337f5b`（v0.13）｜ 用例 **548 → 589**（+41，另删 6 条测假逻辑的）｜ exit 0
> **本版第一次能回答「这个 agent 好不好」，也删掉了一个假装能回答它的东西。**

---

## 一、修之前：有度量的样子，没有度量的实质

`ResponseScorer` 从 v0.1 就在，每轮往 session 写一个 `score`：

```ts
if (response.length > 50) helpfulness += 0.2;      // 越啰嗦分越高
if (toolsUsed.length > 0) accuracy += 0.3;         // 调了工具就算准
if (response.includes('订单')) relevance += 0.2;   // 提到「订单」就算相关
```

两个问题，第二个更严重：

1. **它测不出质量。** 「您的订单您的订单……」凑够 50 字的回复，
   分数高于一句准确的「已发货，顺丰 SF1234567890」。
2. **十三个版本里没有任何代码读过它。** 每轮写一次库，从来没人看。

> 一个没人读的假指标，比没有指标更糟：它让人以为「质量是有度量的」，
> 从而不去建真正的度量。而一旦有人开始信它，它给出的优化方向是**把回答写长**。

删掉它，换成离线评测集 + 三维回归门。

## 二、核心设计的实际结果

### ⚙️ 设计① 指标挂在 EventBus 上，AgentLoop 零改动

```ts
collectFrom(bus, metrics, Date.now());   // 服务端一行
```

这是 v0.4 把事件分发收敛到总线换来的**第三次红利**（前两次是 v0.6 的 SSE 写出器、
v0.10 的安全事件）。埋点如果要往 Loop 里塞 `metrics.inc()`，那才是真的侵入。

**不引入 OTel SDK**：要的是三种指标，OTel 给的是完整 trace 生态 ——
用不上的部分远多于用得上的，而 v0.15 拆服务时依赖越少越好。

标签用白名单校验，未声明的直接抛错：

```ts
it('🔴 未声明的标签直接抛错（白名单是防基数爆炸的第一道闸）', () => {
  expect(() => c.inc({ session_id: 'sesn_1' })).toThrow('不接受标签');
});
```

高基数标签是 Prometheus 的经典事故来源 —— 百万会话 = 百万时间序列 = 内存爆掉。
用例里直接断言**指标输出中不含 sessionId 与 tenantId**。

### ⚙️ 设计② 评测集：口径写在三个地方

评测用脚本化 provider，评的是**编排层**（意图路由 / 工具选择 / 安全脱敏 /
结构化返回），不是模型答案质量。这个限制写在 SPEC、代码注释、脚本输出三处 ——

> 一个说不清自己测了什么的评测，提供的是虚假安全感，
> 而虚假安全感比没有评测更危险。

```
  用例数: 15 ｜ 工具数: 11
  ⚠️  评的是编排层（意图/工具/安全/结构化），不是模型答案质量

  总通过率: 15/15 = 100.0%
    intent       3/3 = 100.0%
    tool_choice  3/3 = 100.0%
    safety       4/4 = 100.0%
    artifact     3/3 = 100.0%
    flow         2/2 = 100.0%
```

**判定逻辑单独测**（10 条用例打 `judgeCase`）—— 一个「永远返回 passed」的评测器
会让所有回归门形同虚设，而那种 bug 跑一遍评测全绿是看不出来的。

### ⚙️ 设计③ 三维回归门：三个维度各自验证过会红

```
  ✓ quality  通过率 100.0%（基线 100.0%，下限 98.0%）
  ✓ cost     每 case 平均 736 tokens（基线 736，上限 810）
  ✓ latency  p95 42ms（基线 42ms，上限 63ms）
```

**门不验证就等于没有门**，所以三个维度各自人为制造一次回归：

| 人为破坏 | 结果 |
|---|---|
| 拆掉安全中间件 | quality ✗ 80.0%，退出码 1 |
| 基线 avgTokens 调到 100 | cost ✗ 736 > 110，退出码 1 |
| 基线 p95 调到 1ms | latency ✗ 40 > 2，退出码 1 |

拆安全中间件那次还顺带证明了三维联动的价值：**成本从 736 涨到 800** ——
原本被拦掉的用例开始真的调模型了。只看质量或只看成本，都会漏掉这个耦合。

## 三、过程中发现的问题

### 🔴 被拦下的工具调用在指标里完全隐形

写 `/metrics` 用例时发现 `agent_tool_calls_total` 对不上。查到 AgentLoop：

```ts
plans.map(async (plan) => {
  if (plan.error) return plan.error;   // ← 直接返回，一个事件都不发
  ...
```

工具不存在 / 参数不合法 / **高风险未通过确认**，这三种情况都走这条路 ——
模型收到一段文字，而 SSE 消费方与指标完全看不见。

**偏低的正是最该被关注的那部分**：v0.12 刚建立的异步确认流，
每一次「等待客户确认」都是一次被拦下的调用，而它在监控上不存在。

补了 `tool_rejected` 事件，计入 `status="rejected"`，**不混进 ok/error** ——
「被拦下」和「执行失败」是两件事，混在一起会让排查走错方向。

### 🟡 一个「先判定再取数」的顺序错误（我自己写的）

评测脚本里意图断言一开始是这样：

```ts
const failures = judgeCase(c, { intent: undefined, ... });  // 先判
if (c.expectIntent) { /* 再去 SSE 里取意图 */ }              // 后取
```

结果 3 条意图用例全红，而实际意图是对的 —— `judgeCase` 拿着 `undefined` 记了一笔，
后面补取根本救不回来。改成先取再判。

这个 bug 有意思的地方在于：**它让一个正确的系统看起来是坏的**。
如果不去追而是直接调低期望，就会把真实的 100% 记成 80% 基线，
从此所有回归对比都建立在错的基准上。
