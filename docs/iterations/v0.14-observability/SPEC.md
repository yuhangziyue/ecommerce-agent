# v0.14 · 可观测与评测

> 起点 `2337f5b`（v0.13）｜ 后继 v0.15 微服务拆分
> **还 v0.1 欠的账**：`ResponseScorer` 是个假指标，跑了十三个版本。

---

## 一、迭代目的

### 🔴 有度量的样子，没有度量的实质

`ResponseScorer` 从 v0.1 就在，每一轮对话都往 session 里写一个 `score`：

```ts
if (response.length > 50) helpfulness += 0.2;      // 越啰嗦分越高
if (toolsUsed.length > 0) accuracy += 0.3;         // 调了工具就算准
if (response.includes('订单')) relevance += 0.2;   // 提到「订单」就算相关
```

两个问题，第二个更严重：

1. **它测不出质量。** 一个「您的订单您的订单您的订单……」凑够 50 字的回复，
   分数高于一句准确的「已发货，顺丰 SF1234567890」。
2. **没有任何代码读它。** 每轮写一次库、存了十三个版本，从来没有人看过。

> 一个没人读的假指标，比没有指标更糟：
> 它让人以为「质量是有度量的」，从而不去建真正的度量。
> 而一旦有人开始信它，它给出的优化方向是**把回答写长**。

### 现在回答不了的问题

| 问题 | 现状 |
|---|---|
| 这个 agent 答得好不好？ | 没有判据 |
| 改了提示词/换了模型，是变好还是变坏？ | 只能靠感觉 |
| p95 延迟是多少？哪一步最慢？ | 没有埋点 |
| 安全规则误杀了多少？ | v0.10 留了审计数据，但**从没算过** |
| 意图识别准确率多少？ | v0.8 做了识别，没做评测 |
| 这次改动让成本涨了多少？ | 账本有数据（v0.11），但没有对比基线 |

**前十三版一直在「造能力」，从没验证过「能力好不好」。**

## 二、核心设计

### ⚙️ 设计① 指标注册表 + `/metrics`

自己实现一个最小的 Prometheus 文本格式导出器，**不引入 OTel SDK**：

- 本项目要的是 counter / gauge / histogram 三种，OTel 带来的是完整的
  trace + context propagation + exporter 生态 —— 用不上的部分远多于用得上的
- 依赖越少，v0.15 拆服务时越容易

埋的点按「**能回答什么问题**」选，不是按「能埋什么」选：

| 指标 | 回答的问题 |
|---|---|
| `agent_turns_total{outcome}` | 有多少轮成功/被拦/出错 |
| `agent_turn_duration_seconds` | p50/p95 延迟 |
| `agent_tool_calls_total{tool,status}` | 哪个工具用得多、错得多 |
| `agent_tool_duration_seconds{tool}` | 哪个工具慢 |
| `agent_tokens_total{kind}` | 用量趋势 |
| `agent_cost_usd_total` | 成本趋势 |
| `agent_blocked_total{by,reason}` | 拦截构成（安全？配额？） |
| `agent_safety_actions_total{stage,action}` | **误杀率的分子** |
| `agent_confirmations_total{outcome}` | 确认流的转化率 |

### ⚙️ 设计② 离线评测集

评测用例是**数据不是代码**：一个 case 声明输入、期望调用的工具、期望的意图、
必须/禁止出现的内容。跑的时候用脚本化 provider，**不打真实 API** ——
否则评测既慢又贵还不确定。

```ts
{
  id: 'order-query-basic',
  input: '我的订单 ORD-20260801-001 到哪了',
  expectIntent: 'order_query',
  expectTools: ['order_lookup'],
  mustContain: ['SF1234567890'],
  mustNotContain: ['13812341234'],   // 手机号必须被脱敏
}
```

**为什么用脚本化 provider 仍然有意义**：评测的是**编排层**——
意图识别路由对不对、工具选得对不对、安全脱敏有没有生效、结构化数据全不全。
这些正是前十三版反复出问题的地方，而它们不依赖模型的具体措辞。

模型本身的答案质量需要真实 API + 人工/模型评审，那超出本版范围，明确写进「不做」。

### ⚙️ 设计③ 三维回归门

```
质量：评测通过率      不得低于基线 - 2%
成本：每 case 平均 token  不得高于基线 + 10%
延迟：p95              不得高于基线 + 20%
```

任一维度越界 → `npm run eval` 退出码非 0。

**三维一起看是刻意的**：只看质量会让人用「多调几次工具、多塞点上下文」
换通过率；只看成本会让人砍掉必要的检查。基线存文件、进版本库，
每次变更都能看到 diff。

## 三、边界

### ✅ 本版做

| # | 事项 | 类型 |
|---|---|---|
| 1 | `MetricsRegistry`：counter / gauge / histogram | 设计① |
| 2 | Prometheus 文本格式导出 + `GET /metrics` | 设计① |
| 3 | 从 EventBus 采集指标（不侵入 AgentLoop） | 设计① |
| 4 | 评测集数据 + `EvalRunner` | 设计② |
| 5 | `npm run eval` 与基线文件 | 设计③ |
| 6 | 三维回归门与退出码 | 设计③ |
| 7 | **误杀率报表**（还 v0.10 的账） | 🔧 |
| 8 | **删掉假的 `ResponseScorer`**，换成诚实的判据 | 🔧 |
| 9 | **【追加 2026-08-15】** `tool_rejected` 事件：被拦下的工具调用不再隐形 | 🔧 |

> **追加说明（9）**：写指标用例时发现 `agent_tool_calls_total` 偏低。
> 查下来是 AgentLoop 的 `if (plan.error) return plan.error;` —— 工具不存在 /
> 参数不合法 / 高风险未通过确认这三种情况**一个事件都不发**，
> 模型收到一段文字，而 SSE 与指标完全看不见。
> **偏低的正是最该被关注的那部分**（被拦下的调用）。补一个 `tool_rejected` 事件，
> 计入 `status="rejected"`，不混进 ok/error —— 「被拦下」和「执行失败」
> 是两件事，混在一起会让排查走错方向。

### ❌ 本版不做

| 事项 | 留给 | 理由 |
|---|---|---|
| 分布式 trace（span/context 传播） | v0.15 | 拆服务后才有跨进程链路可追 |
| 真实 API 的答案质量评审 | 不做 | 需要真实 key + 人工/模型评审，超出本版 |
| Grafana 面板 / 告警规则 | 不做 | `/metrics` 已是标准格式，接哪个后端是部署选择 |
| 按租户拆分指标标签 | 不做 | 高基数标签是 Prometheus 的经典事故来源 |

## 五、风险预判

| 风险 | 影响 | 缓解 |
|---|---|---|
| 指标标签基数爆炸 | Prometheus 内存爆 | 标签只用有限枚举（工具名、outcome），**不放 sessionId/tenantId** |
| 自己实现 histogram 算错分位数 | 决策依据错误 | 用已知分布验算；桶边界显式声明 |
| 评测集用脚本 provider，可能测不到真问题 | 虚假安全感 | **明确写清它测的是编排层不是模型质量**，别声称是全面评测 |
| 回归门太严导致每次都红 | 沦为摆设被绕过 | 阈值留余量（质量 -2% / 成本 +10% / 延迟 +20%），且基线可显式更新 |
| 删 scorer 破坏既有用例 | 回归 | 那 6 条用例本身就是在测假逻辑，**随实现一起删**并在 REPORT 说明 |
