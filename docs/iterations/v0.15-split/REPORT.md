# v0.15 迭代报告 · 微服务拆分

> 起点 `5d43a01`（v0.14）｜ 用例 **589 → 617**（+28）｜ `npm run verify` exit 0
> **这一版验证了前十四版的边界是不是真的。结论：有两处是假的，已修。**

---

## 一、边界是假的，拆的时候才会原形毕露

ROADMAP 从第一版就写着「先在单进程验证边界，稳定后再拆」。兑现时一查就发现：

```ts
// ① AgentLoop 依赖的是具体类，不是接口
private readonly registry: ToolRegistry;
tool.execute(input, ctx)          // ← 直接拿到函数对象调用

// ② 工具依赖模块级单例
let currentStore: RefundStore = new InMemoryRefundStore();
let engine: FlowEngine | null = null;
```

`tool.execute` 是**函数引用，跨不了进程**。只要 Loop 拿到的是「一个能执行的对象」，
工具就永远只能和它待在同一个进程里 —— 这不是性能问题，是架构上的死结。

> 单进程里「模块之间调得通」不等于「边界是清晰的」。
> 判据只有一个：**把中间换成网络，还能不能跑。**
> 换不了，说明之前所谓的分层只是文件夹的分法。

第二处反而是个惊喜：那两个模块级单例**跟着工具搬进 tool-service 就对了** ——
它们本来就属于工具执行层。拆分让它们从「架构污点」变成「服务内部实现细节」。

## 二、核心设计的实际结果

### ⚙️ 设计① `ToolDescriptor`：刻意没有 `execute`

```ts
interface ToolDescriptor {
  name; description; parameters;
  riskLevel;   // ← 必须随描述符过来
}
```

`riskLevel` 是这里最容易漏、漏了最致命的字段：它决定要不要走 v0.12 的异步确认流，
而那是**编排层**的决策。只有工具服务知道风险等级 = 编排层没法拦 = **退款直接执行**。

断电验证过：把 `riskLevel` 写死成 `'low'`，3 条用例立刻转红。

### ⚙️ 设计② 先本地全绿，再做远程

`LocalToolGateway` 存在的唯一意义是让单进程语义**一字不变**：

```
改完 AgentLoop 的工具路径后：Tests 589 passed (589)
```

拆分不该顺带改行为 —— 否则一旦出问题，分不清是拆坏的还是本来就坏的。

### ⚙️ 设计③ 错误语义：基础设施故障 ≠ 业务结论

这是 `RemoteToolGateway` 最重要的部分：

```ts
return {
  content: '工具服务暂时不可达，本次操作未执行（不代表操作失败，也不代表数据不存在）。'
         + '请告知客户系统异常，稍后重试或转人工。',
  metadata: { infrastructureError: true },
};
```

混为一谈的后果是连锁的：模型拿到「查询订单失败」，会告诉客户
**「您的订单查不到」**—— 而真相是我们自己的服务挂了。客户挂了电话去投诉，
而日志里只有一条无害的超时。

这和 v0.12 那句「用户取消了该操作」是**同一类错误的第二次出现**：
把系统自己的问题，用一句听起来像业务结论的话喂给模型。

四种情况分开处置：

| 情况 | 处置 |
|---|---|
| 连不上 / 超时 | 基础设施故障，明说「未执行」「不代表数据不存在」 |
| 5xx | 同上 |
| **4xx** | **我们自己传错了参数**，如实转达，不甩锅给基础设施 |
| 返回体无法解析 | 结果**未知**，要求转人工核实（不能猜） |

### ⚙️ 设计④ 同一套用例跑两种网关

```ts
for (const [name, make] of gateways()) {
  describe(`网关=${name}`, () => { /* 7 条一模一样的断言 */ });
}
```

这是「拆分没改变行为」唯一诚实的证明方式 —— 两边跑同样的断言，
而不是给远程模式另写一套宽松的用例。

## 四、过程中发现的问题

### 🟡 一条测试选错了工具，暴露出参数校验的真实语义

「参数校验失败时不执行」这条用例，最初用 `order_lookup` 传 `{}`。
两种网关都没转红 —— 因为 `order_lookup` 的两个参数**都是可选的**
（订单号「或」手机尾号），`{}` 在 schema 层完全合法，是工具自己在运行时判空。

两种网关给出**一模一样的结果**，这恰恰说明一致性是对的；
错的是我的用例选错了对象。换成 `logistics_check`（orderId 真必填）后正常转红。

> 一条不会红的用例，可能不是实现好，而是它根本没在测你以为的东西。
> 这是 v0.12 之后第二次撞上同一件事。

### 🟢 `ChatProvider` 的签名收窄是个正收益

`chat()` 的工具参数从 `AgentTool[]` 收成 `ToolDescriptor[]` ——
模型只需要名称/描述/schema，**不需要也不该拿到可执行的函数对象**。
`AgentTool` 结构上兼容 `ToolDescriptor`，既有调用方一行没改。
