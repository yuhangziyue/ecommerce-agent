```
  ⚠️  这是模拟值，不是真实网络测量。设置 ANTHROPIC_API_KEY 可打真实 API。
  轮次: 5（取中位数）

模式                    首块延迟(中位)   全量延迟(中位)   全部首块样本
------------------------------------------------------------------------------

流式（v0.4）                        23ms          634ms   [23, 21, 23, 23, 22]
------------------------------------------------------------------------------

  首块延迟：635ms → 23ms，提前 612ms（27.6×）
```

**全量延迟基本不变（635ms → 634ms）—— 这不是遗漏，是本版的要点**：
流式改善的是**感知等待**，不是总耗时。用户判断「卡没卡」看的是第一个字什么时候出现。

### ⚠️ 关于这个数字的诚实性

本机**没有 `ANTHROPIC_API_KEY`，也没有 `ant` 凭证**（已核实），无法发真实请求。
上表是**受控假 provider 的模拟值**，脚本输出里带 `[模拟]` 标记。

- 模拟的是「分块到达」这一行为，块数与间隔是我设的（40×20ms）
- 27.6× 这个倍数**取决于我设的参数**，不是从真实网络测出来的
- 有 key 时脚本自动切到真实 API 并标 `[真实]`，代码路径同一条

**不把模拟值当真实测量报告** —— 这是 SPEC 第四节写死的约束。

## 四、核心设计

### ⚙️ 设计① 一律流式

`ModelProvider` 改用 `messages.stream()` + `finalMessage()`，不再用 `messages.create()`。
理由不只体验：**非流式请求在 `max_tokens` 较大时会撞 SDK 的 HTTP 超时**，
而 v0.12 多步业务流、v0.13 结构化返回都会推高输出长度。流式是更安全的默认值。

最终消息仍交给 v0.3 的 `parseAnthropicResponse` —— 保住并行 `tool_use` 收集行为，
14 条 model-provider 用例作为回归网，全绿。

### ⚙️ 设计② EventBus

`onEvent` 与 `trajectory` 从「Loop 里的两套并行机制」降级为**两个普通订阅者**，
调用方签名不变。新增 `getEventBus()`，v0.6 的 SSE 写出器可直接订阅，不需要再改 Loop。

两条关键性质：**异常隔离**（一个坏埋点不该搞挂对话）、**分发快照**（emit 期间新增订阅者不参与本次）。

## 五、计划外发现：流式绕过了输出脱敏（本版最值得记的一条）

实现完 CLI 逐块渲染后立刻意识到：**`delta` 是模型原始输出，而 `afterTurn` 的脱敏发生在收口阶段
—— 未脱敏的手机号已经打到屏幕上了。**

我自己的测试恰好把这个性质写死了：

```ts
expect(joined).toBe('联系 13812345678');      // delta：原文
expect(reply).toBe('联系 138****5678');       // response：脱敏后
```

这不是 bug，是**流式与输出过滤的固有矛盾**：
过滤需要看到完整文本才能判断（尤其跨块的模式），而流式的意义就是不等完整文本。

**v0.4 的处理是「诚实纠正」**：CLI 累积流式文本，若最终回复与之不同，明确告知并给出准据版本：

```
🛡️  上面的内容已被改写（脱敏/合规），以下为最终版本：
🤖 联系 138****5678
```

**这不是最终解法**。真解法是**流式感知的安全管道**：逐块过滤 + 对跨块模式保留滞后窗口
（例如手机号 11 位，就压住最后 ~15 个字符不发，直到确认不构成敏感模式）。
归 **v0.10 文本安全检测**，已写进该版边界。

> 为什么不现在做：滞后窗口会引入「首块延迟增加」的反向代价，需要和安全分级一起权衡
>（低敏感场景可以不压，高敏感场景宁可牺牲首字延迟）。而分级本身是 v0.10 的核心设计。
> 在没有分级的前提下单独做滞后窗口，只能一刀切，会把本版刚拿到的 27.6× 又还回去一部分。

## 六、承接 v0.3 评审的三项（全部落地）

| 项 | 处理 |
|---|---|
| `resolvePricing` 回退方向与注释相反 | 拆出纯函数 `resolveFromWindows`；早于所有窗口→**最早**窗口（原为最未来，会用未来价算历史账），晚于→最晚窗口；新增 `PricingResolution.resolved` 四态，`CostRecord.pricingResolved` 让非精确命中在对账时可筛出 |
| 价格窗口重叠/缝隙无校验 | `validatePriceWindows`：有序、无重叠、无缝隙、只有首窗可省 `from`、只有末窗可省 `until`，违反直接 throw；**模块加载时校验全表**——录错的价格表在 import 时就炸，不等到某次计费 |
| UTC 边界假设未写进契约 | `PriceWindow` 注释写明「边界按 UTC 日期判定」，并说明若厂商按本地时区截止，切换当天最多 ≤8 小时口径差，**这是显式契约不是疏漏** |
