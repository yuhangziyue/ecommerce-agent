## 二、本版最重要的发现：我把意图识别放错了位置

接进服务端后，四条既有用例同时变红。其中两条是这样的：

```
FAIL 注入攻击输入 → blocked 事件，且不调用模型
AssertionError: expected 1 to be +0
```

**根因**：我把意图识别挂在 `preTurn`（管道最前），排在 `input-filter` **之前**。
意图识别是一次真实的模型调用 —— 这意味着**恶意输入会先烧一次调用再被拦截**。

这直接违背 v0.2 立下的保证：「恶意输入在这里被拦住，**不消耗任何 token**」。
更糟的是它给攻击者提供了免费烧钱的通道：构造一堆注入 payload，每个都能触发一次识别调用。

**修法**：把 `preTurn` 改名为 `enrich`，语义明确为「上下文增强，位置在 `input-filter` 之后」，
并把这个约束写进类型注释 —— 让下一个加中间件的人不需要重新推导这件事。

```ts
/**
 * 上下文增强中间件（画像注入、意图识别）。
 * 位置在 `input-filter` **之后** —— 这是硬约束：
 * 恶意输入必须先被拦住，一次模型调用都不该发生。
 */
enrich?: AgentMiddleware[];
```

**红-绿验证**：把 `enrich` 挪回 `input-filter` 之前 → 注入用例确定性变红
（`intentCalls` 从 0 变 1），恢复后 14/14 绿。

**教训**：v0.2 定的顺序（input-filter 最先）当时的理由是「省 token」，
现在看它同时是一条**安全边界** —— 任何有成本的操作都不能排在过滤之前。
这条在 SPEC 里没写，是靠既有测试抓出来的。

## 三、核心设计

### ⚙️ 设计① 识别失败一律降级，绝不阻断

意图识别是**增强**，不是前置依赖。四条降级路径全部有用例：

| 情况 | 行为 |
|---|---|
| 模型调用抛异常 | `unknown` + 警告日志 |
| 返回非 JSON | `unknown` |
| 意图名不在白名单 | `unknown` |
| 置信度 < 0.6 | `unknown`，**且丢弃槽位** |

最后一条特别重要：低置信度时连槽位也不能用 —— 「猜错比说不知道更糟」。
一个猜错的订单号会让 Agent 去查别人的单子。

`extractJson` 做宽松解析（模型爱加「好的，结果是：」或包 markdown 代码块），
用括号配平 + 字符串状态机而不是正则 —— 正则处理不了 `{"a":"{not json}"}` 这种。

### ⚙️ 设计② 澄清由模型说，不由状态机说

状态机检测到缺槽后，注入的是**信息**：

> 还缺：订单号 或 手机号后 4 位。请用自然的方式向客户询问，**不要机械复述这条提示**；
> 如果客户在前文已经提到过，直接使用不要重复问。

而不是直接回一句「请提供订单号」。理由：客户刚说完一长段，收到一句机械问句的体验是灾难性的。
让模型带着「你还缺什么」这个事实自己组织语言 —— 这正是 v0.7 建 `systemAppends` 的目的。

### ⚙️ 设计③ 切换即清空槽位

```
refund{orderId: ORD-REFUND} → product_search
                            ↓
              slots 清空，previousIntent 记为 refund
```

不清空的话，「退款的订单号」会被带进「查物流」，问出错误的单子。
切换时还会注入一句「之前那个话题的信息不要再带入本轮回答」防止模型串线。
