# v0.8 · 多轮意图识别（Intent）

> 起点 `dc61157`（v0.7）｜ 后继 v0.9 多 Agent 路由
> **v0.9 路由的输入就是本版的输出** —— 没有意图，路由无从谈起。

---

## 一、迭代目的

现在的 Agent 是「一个模型 + 一堆工具」，靠模型自己决定调哪个。这在单轮问答里够用，
但真实客服对话有三个它处理不了的形态：

1. **模糊输入**：客户只说「我要退款」，没给订单号。当前行为是模型自己编一个工具调用，
   参数校验失败后再问 —— 白烧一次调用，且体验是「先出错再问」。
2. **信息跨轮补齐**：客户第 1 轮说订单号，第 3 轮说「那个退了吧」。当前每轮独立，
   槽位不会继承。
3. **话题切换串线**：客户聊完退款忽然问「还有什么好推荐的」，当前上下文里堆着退款相关内容，
   模型容易继续往退款上带。

同时这是 **v0.9 多 Agent 路由的硬前置**：路由要按意图分发，必须先有稳定的意图输出。

## 二、核心设计

### ⚙️ 设计① 意图 + 槽位 + 置信度，一次识别三件事

```
输入：本轮用户输入 + 最近若干轮上下文 + 上一轮意图状态
输出：{ intent, confidence, slots, missingRequiredSlots }
```

电商意图分类（8 类 + unknown）：

| 意图 | 必需槽位 | 说明 |
|---|---|---|
| `order_query` | `orderId` 或 `phoneLast4` | 查订单/物流 |
| `product_search` | — | 找商品、比价、推荐 |
| `after_sales` | `orderId` | 退换货咨询（不含实际退款） |
| `refund` | `orderId`, `reason` | 申请退款（高风险） |
| `logistics` | `orderId` 或 `trackingNo` | 物流异常、催发货 |
| `account` | — | 会员、发票、账户 |
| `complaint` | — | 投诉（应倾向转人工） |
| `chitchat` | — | 寒暄 |
| `unknown` | — | 识别失败的兜底 |

**置信度低于阈值时不做强断言** —— 降级为 `unknown`，让模型按原来的方式自由发挥。
意图识别是**增强**，不该在识别不准时反而限制模型。

### ⚙️ 设计② 意图状态机：继承、澄清、切换

```
        ┌──────────────┐
        │   idle       │
        └──────┬───────┘
               │ 识别出意图
        ┌──────▼───────┐  缺必需槽位
        │  collecting  │──────────────┐
        └──────┬───────┘              │ 生成澄清提示
               │ 槽位齐               │（注入 systemAppends，
        ┌──────▼───────┐              │  不替模型说话）
        │   ready      │◀─────────────┘
        └──────┬───────┘
               │ 新输入意图不同且置信度高
        ┌──────▼───────┐
        │  switched    │ → 丢弃旧槽位，重新收集
        └──────────────┘
```

**关键取舍：澄清不由状态机直接回复用户，而是注入 `systemAppends` 让模型自己问。**

理由：状态机写死的澄清话术会破坏对话连贯性（客户刚说完一长段，收到一句机械的
「请提供订单号」）。让模型带着「你还缺 orderId」这个信息自己组织语言，体验完全不同。
这也是 v0.7 建 `systemAppends` 扩展点的原因。

**槽位继承**：同一意图延续时，上一轮已收集的槽位带过来；意图切换时清空 ——
否则「退款的订单号」会被带进「查物流」，问出错误的单子。

## 三、边界

### ✅ 本版做

| # | 事项 | 类型 |
|---|---|---|
| 1 | `IntentRecognizer`：LLM 识别意图 + 槽位 + 置信度，JSON 解析带兜底 | 设计① |
| 2 | 识别失败 / JSON 不合法 / 置信度低 → 一律降级 `unknown`，不阻断对话 | 设计① |
| 3 | `IntentStateMachine`：槽位继承、缺槽检测、切换检测 | 设计② |
| 4 | 状态落 session metadata，restore 后仍在（跨请求延续） | 设计② |
| 5 | `intent` 中间件：识别 → 更新状态 → 注入 `systemAppends` | 设计② |
| 6 | 缺槽时注入澄清指引（让模型自己问，不替它说话） | 🛒 场景 |
| 7 | 话题切换时注入「旧话题已结束」提示，避免串线 | 🛒 场景 |
| 8 | SSE 增 `intent` 事件，调用方可见识别结果 | 🛒 |
| 9 | `complaint` 意图注入「优先转人工」指引 | 🛒 |

### ❌ 本版不做

| 事项 | 留给 | 理由 |
|---|---|---|
| 按意图分发到领域 Agent | v0.9 | 本版只产出意图，路由是下一版 |
| 意图识别准确率评测 | v0.14 | 需要评测集与基线 |
| 用小模型做识别以省成本 | v0.14 | 先证明有效，再优化成本；换模型要有基线才能判断是否掉点 |
| 槽位自动写入用户画像 | v0.13 | — |
| 多意图并存（一句话两个诉求） | 不做 | 电商客服里罕见，且会让状态机复杂度翻倍 |

## 五、风险预判

| 风险 | 影响 | 缓解 |
|---|---|---|
| 识别多花一次模型调用，成本与延迟翻倍 | 每轮多一次 API 调用 | 识别用**独立的短 prompt**（只喂最近几轮 + 本轮输入，不喂全量历史）；v0.14 再评估换小模型 |
| 模型返回非 JSON | 解析崩溃 | 宽松解析（提取第一个 `{...}` 块）+ 全部失败降级 `unknown` |
| 识别错误导致注入错误指引，反而误导模型 | 体验倒退 | 置信度阈值 + `unknown` 不注入任何指引（保持 v0.7 行为） |
| 状态机与模型的判断冲突 | 模型被限制 | 注入的是**信息**（"你还缺 orderId"）不是**命令**（"必须先问订单号"） |
| 意图识别失败率无法度量 | 不知道好不好 | 本版把 `intent` 放进 SSE 与 session metadata，为 v0.14 评测留下数据 |
