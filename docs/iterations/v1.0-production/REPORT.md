## 二、核心设计的实际结果

### ⚙️ 设计① 取消传播：给没人看的回答付钱是纯浪费

v0.6 的处置是「断开只停止写出，Loop 继续跑完」。那不是浪费 CPU，
是**在给一个已经没人会看的回答付钱** —— 而且 token 是真金白银。

```ts
request.raw.on('close', () => {
  writer.markClosed();
  controller.abort();      // ← v1.0 补上的这一行
});
```

signal 一路传到模型调用（SDK 的 `stream(params, {signal})`）与工具执行。

**取消刻意不是 error**：

```ts
it('🔴 已取消时模型抛 AbortError → 记为 cancelled 而不是 error', ...)
```

把用户关页面统计成系统错误，会让错误率变成一堆噪声，**真故障反而被淹没**。

signal 是可选的 —— 不传时行为与 v0.15 **完全一致**，617 条用例一条没红。
取消能力不该改变没有取消时的语义。

### ⚙️ 设计② 熔断：它保护的是自己，不是下游

```ts
async run<T>(fn: () => Promise<T>): Promise<T> {
  if (this.getState() === 'open') throw new CircuitOpenError(...);  // 直接抛，不执行
  ...
```

熔断器的价值常被说成「保护下游」，但真正的收益在**保护自己**：
下游挂了的时候不熔断，意味着每个请求都要等满超时 ——
事件循环被一堆等死的请求占住，最后是**整个服务一起挂**，
而不只是那一个功能不可用。

半开时**一次失败就重新打开**：探针失败说明下游还没好，再放流量过去
只是重复制造超时。

### ⚙️ 设计③ 高风险工具永不重试 —— 这一版最重要的一行

```ts
const retryable = descriptor?.riskLevel !== 'high';
```

一次超时**最可能是响应丢了，而请求本身已经在下游执行完了**。
重试它就是第二次退款。宁可让客户重来一次，也不能扣两次钱。

`withRetry` 的 `isRetryable` 缺省值也是「都不重试」而不是「都重试」——
**默认值要站在出错时损失最小的那一侧**。

断电验证：把 `retryable` 放开成 `true`，2 条用例立刻转红。

### ⚙️ 设计④ draining ≠ 停机

```
SIGTERM → 置 draining（/healthz 立刻 503）
        → 等 2s 让负载均衡感知
        → app.close() 等在途请求
        → 关资源
```

少了「等 2s」那一步，LB 还没反应过来就已经开始拒绝连接了 ——
表现为部署期间零星的 502，而且**极难复现**。

用例钉住了最关键的那条语义：**draining 期间在途请求仍然成功**。
「不接新活」和「立刻停机」差着所有在途请求的成败。

## 三、诚实说明：部署产物未经验证

开发机上**没有 Docker**：

```
$ which docker docker-compose
docker not found
docker-compose not found
```

Dockerfile 与 compose 文件是按代码实际读取的环境变量写的，拓扑与依赖关系是准确的，
但**没有跑过一次构建**。这个事实标注在三个地方：Dockerfile 首行注释、
`deploy/README.md`、以及 README 的部署段。

> 交付一个自己没验证过的东西，唯一能做的补救是**说清楚它没被验证**。
> 假装它跑过，比不提供它更糟。

## 六、坦白留在原地的东西

不是所有事都该做完，但该说清楚哪些没做、为什么：

| 事项 | 为什么不做 |
|---|---|
| 模型答案质量评测 | 需要真实 API + 人工/模型评审。假装脚本化评测能覆盖它，就是制造虚假安全感 |
| 真误杀率 | 需要人工标注哪些拦截是错的，不是代码能算的 |
| 精确配额扣减 | 需要预留-提交，代价是处理预留泄漏；超发上限有界可测（并发 × 单轮用量），不值得 |
| K8s / 灰度 / 多区域 | 各家基础设施差异太大，compose 已足够表达拓扑 |
| 真实压测数字 | 本机产生不了可信的生产压测结论，给了也是误导 |
| Docker 构建验证 | 开发机无 Docker，已在三处标注 |
