## 二、核心设计的实际结果

### ⚙️ 设计① 租户号从「客户端字段」变成「凭证属性」

本版最重要的一行是这个 diff：

```diff
  session = await Session.create(stores.sessions, {
    userId: body.user_id,
-   tenantId: body.tenant_id,        // 调用方自己说了算
+   tenantId: boundTenant,           // 凭证说了算
  });
```

`boundTenant` 只有两种可能：调用方自己的租户，或者（`admin` 才有的）它被授权代理的租户。
判定收在 `canAccessTenant` 一处 —— **不给 admin 开第二条分支，两处判定迟早会不一致**。

断电验证：把它改回 `body.tenant_id` 并拿掉断言检查，**7 条转红**。

### ⚙️ 设计② 越权一律 404，而不是 403

```
GET /v1/sessions/<别人的会话>   →  404 session_not_found
                                   （与「真不存在」返回完全相同的响应体）
```

403 等于确认「这个 id 存在，只是不属于你」—— 那就是一个**存在性探测接口**，
拿它可以枚举出竞争对手有多少会话、多少退款单。

用例里专门钉了一条：**越权响应与不存在响应必须逐字段相同**。
只统一状态码不统一错误码，照样能被拿来做探测。

唯一的例外是 `tenant_mismatch` 与 `insufficient_scope` 用 403 ——
那两种情况下调用方拥有这个租户，他不是在探测别人，给 404 只会让人排查半天。

### ⚙️ 设计③ 幂等键补的是入口，不是又一道内部防线

v0.3 给退款做了库级幂等，v0.12 让确认单一次性消费，v1.0 让高风险工具永不重试。
**三版都在防重复执行 —— 但入口层完全敞着**：调用方一次网络超时重发，
那是一个全新的请求、全新的 `tool_use_id`、全新的确认单，三道防线一道都不生效。

```
命中 + 体相同 + 已完成 → 重放存下的响应（带 Idempotent-Replay: true）
命中 + 体不同         → 409，**不是返回旧响应**
```

最后一条最容易做错：返回旧响应，调用方会以为自己的新请求生效了 ——
而实际上什么都没发生。这类「看起来成功了但没有」正是这个项目一路在修的东西。

### ⚙️ 设计④ 限流按 principal，且降级方向与缓存相反

```ts
// Redis 挂了降级到**进程内限流**而不是放行
console.warn('[ratelimit] Redis 失败，本次降级为进程内限流');
return this.fallback.consume(key);
```

缓存故障降级只是变慢；**限流故障降级放行等于在故障期间敞开大门，
而故障期恰恰是最需要限流的时候。**

进程内限流在多实例下是 N 倍配额 —— 这个事实写进了 `/healthz` 的 `rate_limit` 字段。
「限流失准」这件事，运维不知道就等于没有限流。

## 三、做的过程中挖出来的三个洞（都不在原 SPEC 里）

按 ROADMAP 第五节的规矩，三个都先回去改了 SPEC 才动手。

### 🔴 洞一：画像根本没有租户维度（立项时发现）

写 PLAN 逐个端点核对归属校验时发现 `user_profiles` 主键是 **`user_id` 单列**。
先用探针在 v1.0 的代码上证实：

```
$ git stash push src/store/migrations.ts && vitest run __probe.test.ts
租户 B 读到的: {"userId":"13800138000","displayName":"张先生",
                "preferences":{"收货时间":"晚上"},"notes":["曾投诉物流延迟"]}
```

**租户 B 拿一个手机号，读到了租户 A 客户的姓名、收货偏好和投诉记录。**

这比会话越权严重：会话 id 是随机串，画像的 key 是**业务主键**，可枚举。
而且不是「忘了加校验」，是数据模型缺一维 —— 只能靠迁移修。

断电验证：让 `get` 忽略租户参数，**10 条转红**。

### 🔴 洞二：模型挂了却回 200（写 P24c 用例时撞出来）

`AgentLoop` 在模型调用失败时吞掉异常，把 `LLM调用失败: xxx` 当作**正常回复正文**返回。
两层后果：

1. 接入方看到一次成功的对话，把这句话原样展示给终端客户 ——
   **v0.12 那个「谎称已处理」的同一个物种**；
2. **本版亲自把它放大了**：幂等键会把这个"成功响应"存 24 小时，
   调用方拿同一个键重试永远拿到那句错误。一次几秒的抖动被固化成一天。

第 2 条正好卡在「不补就会在本版内继续误导验收」的准入线上：
`P24c` 的用例如果不管这里，会因为拿到 200 而"通过"，而它本该证明的东西根本没被证明。

修法限定在本版范围：`/v1/chat/sync` 订阅 `error` 事件 → 502 `upstream_error`，
由既有的 `status >= 500` 规则自动不落幂等记录。**没有动 `AgentLoop`** ——
让 loop 的返回值携带结构化错误是更大的改动，归 v1.2。

### 🔴 洞三：拆分形态下最危险的端点仍然裸奔

主服务堵完之后回头看，v0.15 拆出的 `tool-service` **完全没有认证**：

```
curl -X POST tool-service:3101/v1/tools/execute \
  -d '{"name":"refund_apply","input":{"orderId":"ORD-1","reason":"x"}}'
```

主服务上退款要过高风险确认流（v0.12）。**绕过主服务直打工具服务，那道确认流根本不存在。**
只堵主服务的话，「端点不再裸奔」这句话在拆分形态下就是假的 ——
而拆分形态恰恰是要上规模时才用的形态。

用共享密钥而不是 API Key 那一套：工具服务的调用方只有编排层一个，
没有多租户、没有 scope，引入一整套密钥体系是过度设计。

断电验证：钩子改成直接放行，**2 条转红**（其中一条断言「退款单一条都没落」）。

## 五、偏离 SPEC 的记录

三处中途追加**都先改了 SPEC 再动手**（P16b/c、P16d、第 11 项工具服务密钥、
P24d 上游错误），SPEC 里各自标注了「中途追加 · 原因」。
改完 SPEC 之后没有再出现新的偏离。

一处顺手清理超出了 SPEC 但符合准入线：**删掉 `src/memory/user-profile.ts`**。
它是 v0.1 遗留的**第二套画像实现**，十六个版本零生产引用，只有自己的 5 条用例在跑
—— 与 v0.14 删掉的 `ResponseScorer` 完全同一个物种，也和 v0.2 修的「两套工具实现」同源。
留着的风险是具体的：它没有租户维度，哪天有人把它接上，洞一原样复发。

## 六、坦白留在原地的东西

| 事项 | 为什么不做 | 归属 |
|---|---|---|
| `AgentLoop` 返回结构化错误 | 本版只在 HTTP 层把上游失败翻译成 502。让 loop 自己携带错误类型是跨层改动 | v1.2 |
| 固定窗口在边界放行 2× 速率 | 滑窗代价是每请求多次 Redis 往返。上限有界可算，已写明 | 不做 |
| 密钥自动轮转 | issue + revoke 够了。轮转是运维流程（双活→切换→吊销），不是代码能替人做的决定 | 不做 |
| SSE 响应重放 | 流里有 `confirmation_required` 这类**当时才成立**的事件。改为 409 + `session_id` 指路 | 不做 |
| JWT / 终端用户身份 | API Key 表达的是服务端到服务端。终端用户身份是接入方系统的事 | 不做 |
| 幂等记录的清理任务 | 有 `expires_at` 和索引，但没有定时清理。单表增长可预期，接入方按需加 cron | v1.2 |
| 会话并发写入无锁 | 同一 session 两个请求并发仍会互相覆盖 —— 本版没碰 | v1.2 |
