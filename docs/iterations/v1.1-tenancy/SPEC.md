# v1.1 · 调用方身份与租户边界（P0 收口）

> 起点 `v1.0`（`a6c2f89`）｜ 来源：[架构复盘 2026-08-15](../../ARCHITECTURE-REVIEW.md) 的 🔴 P0 清单

---

## 一、迭代目的

v1.0 的 REPORT 写着「可对外承诺 SLA」。**那句话现在是假的。**

复盘时把 15 个版本当成一个整体从入口重看了一遍，发现一件所有版本都没做的事：

> **系统里从来没有"调用方是谁"这个概念。**

| 现状 | 代码位置 | 后果 |
|---|---|---|
| 没有任何 `onRequest` / `preHandler` | `app.ts` 全文 | 十六个端点全部裸奔 |
| `tenant_id` 从请求体取 | `app.ts:241` | 改一个 JSON 字段就能烧别人的额度 |
| 按 id 取对象的端点零归属校验 | `sessions/:id`、`flows/:id`、`confirmations/:id`… | 猜到 id 就能读别人的会话、批别人的退款 |
| 没有限流 | —— | 一个死循环客户端打爆全部租户 |
| 没有幂等键 | —— | 客户端超时重试 = 重复退款 |

**最后一条尤其讽刺**：v0.3 为退款做了库级幂等，v0.12 为确认单做了一次性消费，
v1.0 为高风险工具关掉了重试 —— 三版都在防重复执行，
**但入口层完全敞着**。调用方一次网络超时重发，前面三道防线一道都不生效：
那是一个全新的请求，全新的 `tool_use_id`，全新的确认单。

这四件事看着是四个功能，其实是**同一个洞的四个面**。补法也只有一个：
**把 principal（调用方身份）做成请求的第一等公民**，让租户、配额、限流、幂等全都挂在它上面。

### 这是第 16 个版本，不是"补丁"

v1.0 是**能力**意义上的终点，不是**可交付**意义上的终点。
15 版一路在修「看起来在工作但实际没有」，这一版修的是最大的一个：
**多租户看起来做完了（账本、配额、配置、安全规则全按租户分），但租户身份是客户端自己说的。**

## 二、核心设计

### ⚙️ 设计① Principal —— 请求的第一等公民

```
Authorization: Bearer ak_live_xxxxx
        │
        ▼
┌───────────────────────────────────────────────┐
│  preHandler: authenticate                     │
│    sha256(key) ──▶ api_keys 表 ──▶ Principal  │
│                                                │
│    Principal { tenantId, keyId, scopes[] }    │
│    挂到 request.principal，全链路唯一身份来源    │
└───────────────────┬───────────────────────────┘
                    ▼
          rateLimit(principal) → idempotency(principal) → handler
```

**三条不可协商的性质**：

1. **库里存哈希不存明文**。库被拖走 ≠ 凭证泄露。明文只在签发那一刻出现一次。
2. **`tenantId` 只能来自 principal**。请求体里的 `tenant_id` 从"数据来源"降级为"断言"——
   与 principal 不一致直接 403，**不是静默覆盖**：静默覆盖会让调用方以为自己写的生效了。
3. **默认开启**。关掉要显式设 `AGENT_AUTH_DISABLED=1`，且启动时打醒目警告。
   延续 v1.0 `isRetryable` 缺省不重试的同一条原则：**默认值站在出错时损失最小的一侧**。

### ⚙️ 设计② 越权一律返回 404，不返回 403

```
GET /v1/sessions/<别的租户的会话id>   →  404 session_not_found
                                        （而不是 403 forbidden）
```

403 等于确认"**这个 id 存在，只是不属于你**"——那就是一个**存在性探测接口**：
攻击者可以拿它枚举出竞争对手有多少会话、多少退款单。

项目里已有同款先例并写明了理由：`/v1/tenants/:id/usage` 对不存在的租户返回全零而不是 404
（`app.ts:774`，「用 404 区分等于给出一个租户是否存在的探测接口」）。**这次把它变成全局规则。**

例外只有一处：`tenant_id` **断言不符**返回 403 —— 那是调用方自己写错了参数，
不是在探测别人，给 404 只会让人排查半天。

### ⚙️ 设计③ 限流按 principal，不按 IP

网关/LB 后面所有请求的 IP 都是同一个，按 IP 限流要么全放要么全封。

```
令牌桶：容量 = burst，速率 = rps
  ├─ Redis 可用  → INCR + EXPIRE 固定窗口，多实例全局准确
  └─ Redis 不可用 → 进程内令牌桶，**每实例一份**（N 个实例 = N 倍配额）
```

降级行为**必须写进文档和 `/healthz`**，不能只在代码里。
「限流在多实例下失准」这件事，运维不知道就等于没有限流。

### ⚙️ 设计④ 幂等键：同 key 不同体 → 409，不是返回旧响应

```
Idempotency-Key: <调用方生成的唯一串>
        │
   ┌────┴─────────────────────────────────────┐
   │ 命中且请求体哈希一致  → 直接返回存下的响应   │
   │ 命中且请求体哈希不同  → 409（不是返回旧的！）│
   │ 命中且仍在处理中      → 409 in_progress    │
   │ 未命中                → 占位 → 执行 → 回填  │
   └──────────────────────────────────────────┘
```

**同 key 不同体返回旧响应是错的**：调用方会以为自己的新请求生效了，
而实际上什么都没发生。这类"看起来成功了但没有"正是这个项目一路在修的东西。

## 三、边界

### ✅ 本版做

| # | 事项 |
|---|---|
| 1 | `api_keys` 表 + 签发/校验/吊销 + `npm run key:issue` 脚本 |
| 2 | `authenticate` preHandler，注入 `request.principal` |
| 3 | `tenantId` 改为只从 principal 取；body 的 `tenant_id` 降级为断言 |
| 4 | **全部按 id 取对象的端点做归属校验**（会话/消息/artifact/安全报表/流程/确认单/画像/租户配置/用量） |
| 5 | `admin` scope：跨租户访问（运营后台用），其余 scope 只能碰自己的租户 |
| 6 | 按 principal 限流（Redis 全局 / 进程内降级），429 + `Retry-After` |
| 7 | `Idempotency-Key` 支持 `/v1/chat/sync` 与 `/v1/confirmations/:id` |
| 8 | `/v1/chat`(SSE) 的幂等：只做 in-flight 冲突检测（理由见下） |
| 9 | `/metrics` `/healthz` 免认证（抓取端与 LB 探针没有凭证），但**不返回任何租户数据** |
| 10 | **用户画像改为按 (租户, 用户) 存**（详见下方「立项时发现的第五个洞」） |

### 🔴 立项时发现的第五个洞：画像是全局的

写 PLAN 时逐个端点核对归属校验，发现 `user_profiles` 的主键是 **`user_id` 单列**
（`migrations.ts:75`）—— 画像根本没有租户维度。

```
租户 A：POST /v1/chat  {user_id: "13800138000"}   ← 写入画像
租户 B：GET  /v1/users/13800138000/profile        ← 读到租户 A 的客户画像
```

而画像里存的正是**称呼、收货偏好、历史投诉备注**，全是 PII。
`user_id` 在真实接入中通常是手机号或会员号，**可枚举**。

这比会话越权更严重：会话 id 是随机串，画像的 key 是业务主键。
不是"忘了加校验"，是**数据模型缺一维**，只能靠迁移修。

修法：主键改 `(tenant_id, user_id)`，`ProfileStore` 全部方法带上租户。
存量行归入 `__anonymous__` 租户 —— 它们本来就没有租户归属，
假装知道它们属于谁是伪造数据。

### ❌ 本版不做（以及为什么）

| 事项 | 为什么 |
|---|---|
| JWT / OAuth2 / 用户级身份 | API Key 表达的是**服务端到服务端**调用。终端用户身份是接入方系统的事，硬塞进来会变成一个半吊子 IdP |
| 密钥自动轮转 | 提供 issue + revoke 就够了。轮转是运维流程（双活期→切换→吊销旧），不是代码能替人做的决定 |
| SSE 响应重放 | 把整条 SSE 流缓存下来重放，语义上是错的：流里有 `confirmation_required` 这类**当时才成立**的事件。重放一条旧流会让客户端弹出一个已经被决策过的确认框 |
| 管理后台 UI / 密钥管理 API | 密钥签发走 CLI + 库。做成 HTTP 接口就需要另一层 admin 认证，鸡生蛋 |
| 分布式限流的完全精确 | 固定窗口在边界处最多放行 2× 速率。滑窗代价是每请求多次 Redis 往返，不值得 —— **但必须写明**这个上限 |
| 请求体加密 / mTLS | 传输层安全归部署（TLS 终结在网关），不归应用 |

## 四、验收判据

### 认证

### 限流

| # | 判据 |
|---|---|
| P17 | 超出 burst → 429 `rate_limited` + `Retry-After` 头 |

### 幂等

| # | 判据 |
|---|---|
